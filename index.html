How P2P / Terminal works

A short guide to sending a file directly to someone else's browser: what happens, what it needs, and what it doesn't do.

Overview

P2P / Terminal connects two browsers directly using WebRTC. Once a session is linked, a file you send travels straight from your device to your peer's over an encrypted data channel; it is never uploaded anywhere in between. A small signaling server only helps the two browsers find each other; it sees connection metadata, never file contents.

Start a session

  1. Create a session to get a six-character room code, plus a one-click join link with its own QR code — share whichever is easiest: read out the code, paste the link, or let your peer scan the code with their phone. Optionally set a PIN first: a room with a PIN rejects anyone who has the code but not the PIN, and a wrong guess never occupies the room's one open seat. The PIN is never included in the link or QR code — share it through a different channel than the one you shared the code through.
  2. Join a session by entering that code, opening the link, or scanning the QR code on the other end — plus the PIN, if your peer set one. The two browsers negotiate a direct link automatically.
  3. Watch the status at the top of the Transfer tab: it moves from awaiting peer to connected once the link is open.

Send files and folders

Drop one or more files, or an entire folder, onto the panel — or click it to browse for files, or use "choose a folder instead" — once a session is connected. A single file sends as-is; multiple files or a folder are zipped together in your browser first (preserving the folder structure), then the resulting file is split into small chunks and streamed over the data channel, with a live readout of progress, speed, and time remaining.

Before sending, your browser computes a SHA-256 hash of the file. Your peer computes the same hash from what it received and the app compares the two automatically, so you can tell at a glance whether the transfer arrived intact — zip included.

Set a zip password before sending to encrypt the archive itself, not just the connection — useful if the file might get forwarded, saved, or opened later outside this app. Setting one zips even a single file, since that's the only way to apply it. The password travels to your peer the same way a room PIN does: never through this app, so tell them separately.

Privacy and security

  • File data travels over a direct, encrypted WebRTC connection between the two browsers involved, not through any server.
  • The signaling server only relays connection setup messages and never stores or inspects file contents.
  • A room accepts exactly two people. It closes as soon as either one disconnects, and the code cannot be reused afterward.
  • Integrity is verified end to end with a SHA-256 checksum, shown in full on the Transfer tab.

Requirements and limitations

  • A modern browser with WebRTC support: recent Chrome, Firefox, Edge, or Safari.
  • Both people need the page open at the same time; there is no way to queue a file for later.
  • Connections are established with public STUN servers only. On a strict corporate network or firewall, a direct link can occasionally fail to establish.
  • The sender holds the whole file in memory during transfer, so very large files are limited by available RAM.

What this measures

  • Ping, jitter, download, and upload are all measured against this app's own server over regular HTTPS — not your WebRTC link to a peer.
  • A file sent in the Transfer tab travels browser-to-browser directly, so it's often faster than this number, especially on the same network.
  • Results vary with your ISP, Wi-Fi, VPN, and how busy this server's region is right now.
