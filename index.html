How P2P / Terminal works

A short guide to sending a file directly to someone else's browser: what happens, what it needs, and what it doesn't do.

Overview

P2P / Terminal connects two browsers directly using WebRTC. Once a session is linked, a file you send travels straight from your device to your peer's over an encrypted data channel; it is never uploaded anywhere in between. A small signaling server only helps the two browsers find each other; it sees connection metadata, never file contents.

Start a session

  1. Create a session to get a six-character room code, then share it with your peer however you'd like: chat, text, a call.
  2. Join a session by entering that code on the other end. The two browsers negotiate a direct link automatically.
  3. Watch the status at the top of the Transfer tab: it moves from awaiting peer to connected once the link is open.

Send a file

Drop a file onto the panel, or click it to browse, once a session is connected. The file is split into small chunks and streamed over the data channel, with a live readout of progress, speed, and time remaining.

Before sending, your browser computes a SHA-256 hash of the file. Your peer computes the same hash from what it received and the app compares the two automatically, so you can tell at a glance whether the file arrived intact.

Privacy and security

  • File data travels over a direct, encrypted WebRTC connection between the two browsers involved, not through any server.
  • The signaling server only relays connection setup messages and never stores or inspects file contents.
  • A room accepts exactly two people. It closes as soon as either one disconnects, and the code cannot be reused afterward.
  • Integrity is verified end to end with a SHA-256 checksum, shown in full on the Transfer tab.

Requirements and limitations

  • A modern browser with WebRTC support: recent Chrome, Firefox, Edge, or Safari.
  • Both people need the page open at the same time; there is no way to queue a file for later.
  • Connections are established with public STUN servers only. On a strict corporate network or firewall, a direct link can occasionally fail to establish.
  • The sender holds the whole file in memory during transfer, so very large files are limited by available RAM.
